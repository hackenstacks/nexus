    Rohaun — Deanonymized Chain (from meeting)¶

    Konrad referenced Rohaun as a chain that was repeatedly deanonymized.

    Separately: a 2025 paper demonstrated that I2P was successful in identifying a node. This is a known, published attack vector.

    What this means for NeXuS: - I2P-native does not mean anonymous-by-default — I2P has a demonstrated node identification vulnerability - NeXuS cannot rely on I2P alone for anonymity - The multi-network stack (Tor + I2P + Yggdrasil + Reticulum) is not optional — it is the defense-in-depth response to exactly this class of attack - ZKP layer adds separation between chain activity and node identity even if the transport is compromised - Ghost Gate egress control prevents correlation attacks at the packet level

    Attack vector: timing / live behavior alignment.

    The Paper¶

    "Time will Tell: Large-scale De-anonymization of Hidden I2P Services via Live Behavior Alignment (Extended Version)" Hongze Wang, Zhen Ling, Xiangyu Xu, Yumingzhi Pan, Guangchi Liu, Junzhou Luo, Xinwen Fu Submitted: December 17, 2025 — Accepted: NDSS Symposium 2026 https://arxiv.org/abs/2512.15510

    How the Attack Works¶

    • Deploy 15 floodfill routers passively for 8 months collecting router information
    • Actively probe target hidden services to generate detectable behavior
    • Analyze when routers join and disconnect from the network — on/off timing patterns
    • Match those behavioral signatures against target hidden services
    • Result: successfully deanonymized all controlled hidden services in real-world validation

    This is not a content attack. It is a behavioral fingerprinting attack — the node's pattern of being online/offline becomes its identity.

    What This Means for NeXuS¶

    • A NeXuS node that runs 24/7 has a stable behavioral signature — harder to correlate
    • A node with irregular uptime (laptop, mobile) leaks its on/off pattern as a fingerprint
    • I2P-native DIVA inherits this exposure — every node committing to DIVA over I2P has a behavioral profile
    • Ghost Gate must address behavioral fingerprinting, not just packet-level timing
    • Always-on nodes are more resistant by design — NeXuS nodes should aim for continuous uptime
    • ZKP layer still holds: even if the node's I2P identity is revealed, the chain sees a proof not the node

    Clarification — Konrad and the paper agree¶

    Both say the same thing: intermittent (off and on) = easier to fingerprint. - Always on → no on/off events → no behavioral signature - Frequently off and on → every reconnect is a data point → pattern becomes fingerprint

    Why NeXuS Overcomes This (with refinement)¶

    1. Scale defense — the attack doesn't scale trivially against thousands of nodes with similar uptime patterns. Identifying a specific node requires narrowing the candidate pool. Large NeXuS network = harder correlation.
    2. Limited I2P exposure — NeXuS nodes don't run I2P continuously. I2P is used specifically for DIVA commits. Less exposure = smaller behavioral surface than a full-time I2P node.
    3. The nuance — a node that connects briefly, submits a ZKP proof, then disconnects on a regular schedule creates its own distinctive pattern. The fix is jitter: randomize when DIVA commits happen, not just whether the node is connected.

    Actions¶

    • Add jitter to ZKP commit timing — randomize submission delay, not just connection timing
    • Maintain persistent I2P connection with cover traffic rather than connect-submit-disconnect cycle
    • Add behavioral fingerprinting resistance to Ghost Gate spec
    • Raise with Konrad on follow-up call — does Proof of Storage challenge/response create a predictable behavioral signature?

    Decision Log¶

    CometBFT — Removed from Node Spec (2026-04-06)¶

    Decision: CometBFT removed from the three-tier settlement table. Tier 3 marked as TBD.

    What CometBFT was: Tier 3 settlement — irreversible, high-value, cross-network transactions. The BFT consensus engine extracted from Cosmos SDK (formerly Tendermint). Was intended for edge cases where DIVA Tier 2 finality wasn't enough guarantee — e.g. massive NeXiuM cashouts to another network.

    Why it was removed: - We locked NO Cosmos SDK — too heavy for laptop hardware (the founding constraint of NeXuS nodes) - CometBFT is the engine Cosmos SDK is built on. They are separable in theory but tightly coupled in practice. The weight concern carries over. - 99.9% of NeXuS transactions never need Tier 3. Routing rewards, purchases, royalties all settle at Tier 2. CometBFT is a full international banking team hired for a transaction that almost never happens. - DIVA Proof of Storage with sufficient confirmation depth is likely the right Tier 3 answer at NeXuS scale — but that needs to be confirmed with Konrad.

    What replaced it: Tier 3 = "Deep DIVA confirmation — mechanism TBD. Raise with Konrad on follow-up call."

    What to ask Konrad: Does Proof of Storage at N confirmations provide the same irreversibility guarantee that CometBFT was meant to provide? If yes — Tier 3 is solved natively. If no — what is his recommended pattern for high-value irreversible settlement on DIVA?

    Two Chains¶

    Every node runs two layers:

    Layer Lives What it is
    Client-side database On the node, local Sovereign history — every action, master-key-signed, hash-linked
    DIVA chain Across the network, I2P-native Public witness — receives ZKP proofs, holds NeXiuM balances + creator economy state

    Konrad confirmed: The personal chain is a client-side database, not a distributed chain.

    Konrad confirmed: DIVA is moving to Proof of Storage — not voting. Nodes prove they are storing chain data. This replaces the voting/locking phase described in earlier DIVA docs.

    The Economy — One Chain, Two Flows¶

    Both economic flows use NeXiuM on DIVA. No second payment chain in docs.

    Flow How
    Proof of Service Node routes traffic → Ghost Gate records → ZKP → DIVA commit → NeXiuM credited to cold address
    Proof of Purchase Fan pays creator in NeXiuM → license issued on DIVA → IPFS content unlocks → royalties distributed on-chain

    ZKP — gnark PLONK. Locked.¶

    Universal setup. No trusted ceremony. Zero Trust aligned. The chain sees proof of valid work — never the identity behind it.

    Full Transaction Flows¶

    Proof of Service (Node Earns NeXiuM)¶

    1. Node routes traffic (Medusa/Tor)
2. Ghost Gate checks Three Heads (AI fingerprint + Operating Key + User Permit)
3. Ghost Gate writes proof_of_contribution (local)
4. Client-side database logs entry (hash-linked, master-key-signed)
5. ZKP generated (gnark PLONK) — proves valid work, reveals nothing
6. PUT /transaction → DIVA over I2P
7. DIVA consensus confirms (Proof of Storage)
8. nexus:nexium:<node_key_hash> balance credited
9. NeXiuM accumulates in cold address (never in transaction graph)

    Proof of Purchase (Fan Buys Content)¶

    1. Creator published: nexus:content:publish on DIVA (plaintext — discoverable)
   File encrypted on IPFS
2. Fan queries DIVA → finds listing, price in NeXiuM, IPFS CID
3. Fan generates ephemeral wallet (BIP32 child key from master key)
   Transfers spending amount: cold address → ephemeral wallet
4. Fan sends NeXiuM → DIVA: nexus:content:purchase (encrypted)
   DIVA consensus confirms
5. Creator's node sees confirmed purchase → generates license key
   Encrypts with fan's Ed25519 public key → commits to DIVA
6. Fan decrypts license key → decrypts IPFS content → file downloads
7. Royalty split: creator reads nexus:stake:* → distributes NeXiuM to each %
   nexus:royalty:distribute committed to DIVA — permanent, automatic, forever
8. Both personal databases log the event (sovereign local record)
9. Ephemeral wallet dissolves — zero balance, no history linked to cold address

    DIVA Namespace Structure¶

    The namespace keys are I2P addresses. A node's identity on DIVA is its I2P destination. Privacy is structural — no separate anonymization layer needed. Only the node holding that I2P keypair can write to its namespace. This may resolve open question #2 (identity-locked writes) — I2P keypair ownership IS the write lock.

    nexus:nexium:<i2p_address>      →  NeXiuM balance
nexus:content:publish           →  content metadata, IPFS CID, price (public)
nexus:content:purchase          →  encrypted license key (private)
nexus:royalty:distribute        →  encrypted royalty proof (private)
nexus:stake:create              →  stakeholder shares offered (public)
nexus:stake:purchase            →  encrypted stake record (private)
nexus:node:register             →  node identity (public)

    Public entries: plaintext, discoverable. Private entries: data field encrypted Ed25519 → X25519 (libsodium). Network sees transaction occurred. Only parties can read it.

    The I2P address as namespace key means: - Identity = I2P destination (cryptographic, not human-assigned) - Write authority = possession of the I2P private key - No separate identity system needed for namespace ownership - Cannot be linked to real-world identity without the private key

    Master Key Architecture¶

    Master Key (cold, never leaves the node)
  → signs genesis block = node's self-signed certificate
  → derives Session Key (hot, rotating)
      → signs DIVA commits
      → signs Ghost Gate permits
      → signs daily audit entries
  → derives Ephemeral Wallets (BIP32 child keys, spend-time only)
