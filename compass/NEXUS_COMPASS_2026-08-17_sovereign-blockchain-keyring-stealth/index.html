    1. The CA De-Anonymization Problem¶

    What was discovered¶

    The NeXuS CA (step-certificates, local step-ca) was identified as a potential de-anonymization vector. The concern: if public metadata from a cert is observed by an external party, it fingerprints the node operator.

    What leaks from a TLS cert¶

    Data point Risk
    O=NeXuS CA, CN=NeXuS CA Intermediate CA in issuer Identifies operator as NeXuS
    SAN 192.168.1.15 Reveals LAN IP — node-specific
    Root fingerprint 99f174... Correlates all certs from same CA
    Key linkability Same key across sessions = same node

    What does NOT leak (current setup)¶

    • CA listens on 127.0.0.1:9000 only — no external exposure
    • Private CA — zero CT log submissions
    • No OCSP requests to external servers

    The rule derived¶

    For .onion and .i2p services: no TLS certs needed at all. Tor and I2P have self-authenticating naming — adding TLS adds a fingerprint where none existed. TLS certs are for LAN-to-LAN node communication only.

    2. The Anonymity Set Solution — Uniform Public Metadata¶

    The concept¶

    All NeXuS nodes present identical public metadata — same org name, same cert template, same SAN pattern. An observer can identify a node as a NeXuS node but cannot identify which NeXuS node or whose node.

    This is the same principle as Tor Browser — all users present identical fingerprints. The fingerprint identifies the crowd, not the individual.

    Standardized cert template (NeXuS Node Standard)¶

    Subject:   O=NeXuS Network, CN=nexus-node   ← same for ALL nodes
SANs:      localhost, 127.0.0.1, local.host.local  ← NO real IPs
Issuer:    O=NeXuS CA, CN=NeXuS CA Intermediate CA ← shared root
Algorithm: ECDSA P-256
Duration:  24h (rotates daily)
Key:       UNIQUE per node, ROTATES per epoch

    What's shared vs unique¶

    Layer Standardized (public) Unique (private)
    Root CA Same cert ships in every .sfs —
    Cert template Subject, SANs, duration, algorithm Private key per node
    Response headers Same server header (or none) —
    Node behavior Same port layout, same API shape Config, content

    .sfs connection¶

    The NeXuS root CA ships inside nexus-base.sfs. Every node booting from it inherits the same public identity. On first boot a script generates the node's unique private key, signs a cert from the shared CA using the locked template. No deviation allowed.

    3. HD Key Rotation — nexus-keyring¶

    The core design¶

    Inspired by virtual credit card one-time-use numbers and HD (Hierarchical Deterministic) wallets. The master key never leaves the machine. From it, the node continuously derives ephemeral child keys that rotate automatically.

    password + local_random_seed
         ↓ HKDF / PBKDF2 (200,000 rounds)
    master_secret  ← never transmitted, never leaves disk, encrypted at rest
         ↓ derive(unix_epoch // rotation_interval)
    child_key_001  → TLS cert valid 24h
    child_key_002  → TLS cert valid 24h  (rotates in, 001 discarded)
    child_key_003  → ...

    Key derivation detail¶

    seed_file  = /dev/urandom 32 bytes   ← stored encrypted (age)
master     = HKDF(PBKDF2(password, seed_file, 200000), "nexus-v1")
child_key  = HKDF(master, str(epoch // rotation_seconds), "nexus-cert-v1")

    Neither half alone is useful: - Seed without password → useless - Password without seed → useless - Together → unlock derivation chain

    Privacy properties achieved¶

    Property Mechanism
    Unlinkability Two certs from same node have different public keys — cannot correlate
    Forward secrecy Old keys discarded — past sessions not decryptable if current key compromised
    Shared anonymity set Issuer = NeXuS CA — observer knows it's a NeXuS node, not whose
    Recovery password + seed file → re-derive current epoch key
    No online master Master never hits the network — only derived children do

    Precedents¶

    • Tor relays: onion service keys rotate on schedule
    • Signal: pre-keys rotate after use
    • BIP32 HD wallets: master seed → child keys, master never transmitted

    nexus-keyring tool design (not yet built)¶

    nexus-keyring init
  ├── generates random_seed (256 bits, age-encrypted to password)
  ├── derives master_secret → stays in kernel keyring (keyctl)
  └── writes seed file to ~/.config/nexus/keyring/seed.enc

nexus-keyring rotate
  ├── derives child_key = HKDF(master, current_epoch)
  ├── generates CSR, sends to local step-ca
  ├── atomic swap: write new cert.pem + key.pem
  └── SIGHUP to web server → zero-downtime cert reload

nexus-keyring daemon
  └── OpenRC service, auto-rotates on schedule, fully silent

    Session decrypt (the time machine property)¶

    The master never rotates. Child keys are derived deterministically from master + epoch. To decrypt a session from 6 months ago: derive the key for that epoch, decrypt. The master is the time machine. This is the property the user described as "go back to a previous session and be able to decrypt."

    Rotation interval recommendation¶

    • LAN nodes (rarely externally observed): 24h
    • Higher-exposure nodes: 6h or 1h
    • step-ca issues certs in milliseconds — rotation cost is negligible

    4. Stealth Addresses — Creator Monetization Without Identity¶

    The problem¶

    A creator publishes a recipe book (or any content). They want to continue receiving payment indefinitely without ever being identified. Payments must be: - Unlinkable (each payment goes to a different address) - Uncorrelatable (no observer can link payments to the same recipient) - Claimable by the creator at any time (even months later) - Uncorrelatable to the creator's identity

    The solution: stealth addresses (Monero's model)¶

    The creator holds a stealth meta-address — a pair of public keys: 

    scan_pub   ← used to find incoming payments (can be shared with auditor)
spend_pub  ← used to claim payments (never shared)

    The stealth meta-address is embedded in the content at creation time, signed by the creator's key. The signature proves the address belongs to the original author without revealing who that author is.

    Payment flow¶

    1. Buyer sees content with embedded stealth_meta_address
2. Buyer's client generates ephemeral key r
3. one_time_address = hash(r × scan_pub) × G + spend_pub
4. Payment sent to one_time_address (looks random to all observers)
5. r embedded in transaction (public, meaningless without scan_priv)

    Creator scanning (can happen at any time, even years later)¶

    for each transaction:
    check: hash(scan_priv × r) × G + spend_pub == this address?
    if yes → this payment is mine
    derive spend_key = hash(scan_priv × r) + spend_priv
    claim the payment

    What an observer sees¶

    • A payment to a random-looking address
    • Cannot link to creator identity
    • Cannot link to other payments from the same content
    • Cannot link to other payments to the same creator
    • Creator could be dead — their estate scans with master key to claim 10 years of royalties

    Perpetual royalties — the content carries the rule¶

    recipe_book.nxs
  ├── content (encrypted)
  ├── stealth_meta_address = (scan_pub, spend_pub)
  ├── royalty_rate = 0.15
  └── creator_sig  ← proves address belongs to original signer
                     without revealing who the signer is

    The royalty rule travels with the asset. Every compliant NeXuS node serving or relaying the content routes the royalty cut to the stealth address. Non-compliant nodes violate protocol and are treated accordingly by the network.

    Scan efficiency at scale¶

    Monero solves bulk scanning via view tags — a 1-byte hint attached to each transaction. Lets the scanner skip 99%+ of transactions without full computation. NeXiuM inherits this.

    6. The NeXuS-Native Blockchain — OS-Integrated, State-Only, Prune-After-Consensus¶

    The unprecedented insight¶

    No blockchain exists that is part of an OS. No OS has a blockchain as a native primitive. Every blockchain runs on an OS. NeXuS flips this: the blockchain IS part of the OS. The node is not an app. State sync is like syncing the clock — it just happens at the OS level.

    This is a genuine architectural first.

    The pruning insight¶

    Traditional blockchains keep full history because history is the proof of current state.

    NeXuS inverts this: consensus on current state IS the proof. History is scaffolding.

    Once all nodes agree on "who has what" and that agreement is cryptographically signed — the transactions that produced that state are no longer needed. You needed the scaffolding to build the floor. Once you're standing on it, the scaffolding comes down.

    The block structure¶

    Block N:
  ├── state_root      = merkle_hash(all current balances + capabilities)
  ├── delta           = compressed diff from block N-1 state
  ├── consensus_sigs  = signatures from participating nodes
  ├── timestamp
  ├── prev_state_root = links to block N-1 (proves continuity)
  └── zk_proof        = proves this state transition is valid
                        without revealing individual transactions

Block N transactions: PRUNABLE after block N is finalized and dispute window passes

    Consensus flow (before each block)¶

    1. Collect all transactions since block N-1
2. Each node computes resulting state (who has what)
3. Nodes exchange state_root hashes
4. If supermajority agree on same state_root → block finalized
5. ZK proof generated: "state N is valid transition from state N-1"
6. Transactions that produced this state → scheduled for pruning
7. After dispute_window expires → transactions deleted
8. Only state_root + delta + zk_proof survive

    ZK proofs — the mechanism that makes pruning safe¶

    ZK proof: "state_root_N is a valid transition from state_root_N-1"
         ← verifiable in milliseconds by any node
         ← reveals nothing about individual transactions
         ← cryptographically proves history without storing history

    New node joining the network: 1. Downloads current state snapshot (who has what right now) 2. Downloads ZK proof chain (proves this state is valid) 3. Fully verified and operational in seconds 4. Does not need a single historical transaction 5. Does not need to replay years of blockchain history

    Storage comparison¶

    Chain Storage New node sync History
    Bitcoin ~600GB Days Forever
    Ethereum ~1TB+ Days–weeks Forever
    NeXuS Current state + dispute window only Seconds Pruned after consensus

    The dispute window¶

    The only history retained is the dispute window — long enough for any participant to challenge a fraudulent state transition. Suggested: 72 hours to 7 days depending on the application. After the window: every transaction is gone. Only the ZK proof of the finalized state survives.

    Precedents (partial implementations, never OS-integrated)¶

    • Mimblewimble (Grin, Beam) — transaction cut-through: intermediate txs disappear, chain shrinks
    • Nano — each account has its own chain, only current balance matters
    • Ethereum stateless clients — clients with no history, only state proofs (still global VM)
    • Celestia — separates data availability, execution, consensus (still external to OS)

    None are OS-integrated. None achieve full prune-after-consensus. NeXuS combines all insights and goes further.

    "Who has what" is broader than money¶

    When the blockchain is IN the OS, "who has what" means: - Balances (NeXiuM) - Capabilities (file permissions, access grants) - Content licenses (recipe book ownership) - Node identities (public key → node mapping) - Reputation scores (Proof-of-Witness)

    The state is holistic. The blockchain is not a separate financial layer — it IS the OS permission and identity system.

    Smart contracts in this model¶

    Contracts are not global programs running on every node. They are state transition rules enforced locally by the OS: - The contract is a kernel policy, not a blockchain program - The OS is the VM - Parties agree on rules; the OS enforces them locally - Consensus is only about the resulting state, not the execution details

    8. The Vestal Protocol — Loyalty Baked Into Math¶

    STATUS: ✅ DEFINED
    Sources: ~/Pictures/nexus/The_Vestal_Protocol_Reward_Tiers.png · ~/manuals/vestal-protocol.md
    Name origin: Vestal Virgins of ancient Rome kept the sacred city fire burning 24/7. A node that breaks uptime lets the NeXuS flame die.
    Philosophy: Showing up is the work, and unbroken service is the proof of contribution.

    What it solves¶

    The network needs reliable nodes. Reliability must be incentivized mathematically, not socially. The Vestal Protocol is the Proof-of-Uptime participation and reward layer — earns nodes NeXiuM for staying online, punishes inconsistency harshly, redistributes forfeited wealth to loyal survivors, rewards long-term loyalty exponentially.

    1. The Heartbeat — 60-Second Proof of Life¶

    Nodes sign and submit a cryptographic heartbeat to the DIVA ledger every 60 seconds. Gap > 5 minutes → flagged Offline instantly.

    This IS the consensus participation signal. The heartbeat cadence aligns with block finalization — nodes signing heartbeats are the nodes whose state_root signatures count toward consensus.

    2. The 48-Hour Earn / Vest Cycle¶

    Hour 0–24  — EARNING WINDOW
  Continuous unbroken uptime earns 1 Vestal Credit
  Credit is LOCKED — cannot be spent or moved

Hour 24–48 — VESTING WINDOW
  Credit vests gradually (see Loyalty Function below)
  Go offline at Hour 47 → V = 0, streak resets to zero

Hour 48    — SETTLEMENT
  Credit 100% vested → locked permanently into PLUTUS Vault (Ring 02)
  Spendable NeXiuM. Yours forever. Safe to go offline now.

    3. The Loyalty Function — The Math¶

             ┌ 0                          if t < 24h
V(t) =   ┤ C × ((t − 24) / 24)       if 24h ≤ t < 48h
         └ C                          if t ≥ 48h

    Where V(t) = vested credit at time t, C = total earned credit, t = continuous unbroken uptime in hours.

    Time Vested
    t = 24h 0% — seed planted, nothing vested yet
    t = 36h 50% — halfway through vesting
    t = 48h 100% — fully vested, locked into PLUTUS Vault
    Disconnect at t = 47h 0% — unvested credit fully forfeited, streak reset

    4. Springboard Economics — The NeXuS Inversion¶

    When a node forfeits unvested credits, those credits do not disappear. They are immediately redistributed into the epoch pool for surviving nodes.

    The NeXuS Inversion: Other nodes leaving the network makes staying more valuable for loyal nodes who remain. During network stress, nodes that hold the line inherit the accumulated wealth of those who left. No death spiral — loyal nodes are paid by disloyal nodes.

    This is the slashing mechanism: Byzantine nodes don't just lose their reward, they fund the honest ones.

    9. ZK-STARKs — Why and Which¶

    Why STARKs over SNARKs — The Quantum Decision¶

    ZK-SNARKs ZK-STARKs
    Trusted setup Required — if any participant cheats, the whole system is permanently compromised None — trustless by design
    Quantum resistance No — elliptic curve based; Shor's algorithm breaks it Yes — hash-based; Grover's algorithm only halves security (fixable by doubling hash size)
    Proof size ~200 bytes ~50–200KB
    Verification Fast Fast
    Sovereignty fit Poor — external trust baked into cryptography Perfect — no external dependencies

    STARKs were specifically hardened against quantum computing by moving to larger field sizes and hash output sizes (targeting 256-bit security) to pre-empt Grover's algorithm. SNARKs cannot be patched for quantum — the elliptic curve foundation collapses under Shor's.

    The NeXuS permanent record (STARK proofs of finalized state) must be verifiable in 50 years. STARKs survive quantum advancement. SNARKs do not.

    The trusted setup is the dealbreaker: SNARKs require a ceremony where if even one participant had quantum capability at the time, the entire proof system is silently broken forever. NeXuS cannot accept that. STARKs have no ceremony.

    11. VeeDo — STARK-based VDF (The Black Box Engine)¶

    Repo: ~/git/veedo
    Source: StarkWare
    What it proves: "I ran this delay function for N iterations correctly" — nothing more, nothing less.

    MiMC Delay Function¶

    prime = 0x30000003000000010000000000000001  # 126-bit field
pow   = (2 * prime - 1) / 3               # cube root exponent

# Each iteration: cube → MDS matrix mix → add constants
# Repeat 335 million times → 3.5 minutes, unavoidable even with infinite parallelism

    Prover inversion trick¶

    The prover runs the INVERSE function (cube root → computationally cheap in the field) to generate the trace. The verifier checks the FORWARD direction. This asymmetry is why the delay is real — forward is hard, inverse is easy, verification is fast.

    MDS Matrix (deployed values — use these, NOT the Sage reference values)¶

    MM_MAT00 = 0x109bbc181e07a285856e0d8bde02619
MM_MAT01 = 0x1eb8859b1b789cd8a80927a32fdf41f7
MM_MAT10 = 0xdc8eaac802c8f9cb9dff6ed0728012d

    VeeDo's role in NeXuS¶

    Use Mechanism

    Block randomness beacon Previous block hash → VDF during dispute window → next block's canonical randomness

    Key limitation: VeeDo only proves VDF computation. It is NOT the general state transition prover. That is proving/crates/stwo.

    12. stwo-cairo + proving — The Production Engine¶

    Repos: ~/git/stwo-cairo (stable snapshot) · ~/git/proving (active development — use this)
    Source: StarkWare — Apache 2.0
    Status: Production. Runs StarkWare's SHARP infrastructure securing Starknet today. Not research.

    Circle STARKs — Why M31 Changes Everything for NeXuS¶

    M31 = 2^31 - 1  ← Mersenne prime, fits in one 32-bit machine word

Reduction mod M31:
  result = (a * b >> 31) + (a * b & 0x7fffffff)
  ← 3–4 CPU instructions vs complex 256-bit Montgomery reduction
  ← E6520 SSE4.2: pack 4 × M31 per SIMD register = 4× throughput
  ← SIMD-native, rayon-parallelised — scales on commodity hardware

    The field was chosen because M31 arithmetic vectorises cleanly on real CPUs. The E6520 compute concern from earlier largely disappears with Circle STARKs.

    Extension Field Tower¶

    M31   → 31-bit base field (hardware speed)
CM31  → M31[i], i²=-1 (complex Mersenne, quadratic extension)
QM31  → CM31[j], j²=i (quaternion Mersenne, degree-4 extension)

QM31 security: 4 × 31 = 124 bits — from 32-bit operations

    Strong security without 256-bit arithmetic. Perfect for constrained nodes.

    The Recursive Proof Tree — Prune-After-Consensus Made Concrete¶

    N block proofs (leaf proofs, one per NeXuS block)
  ↓ binary folding via circuit_multiverifier
  ↓ each pair: prove both children with one multiverifier circuit
  ↓ ceil(log2(N)) layers — balanced, predictable
  ↓ 1 root proof

100 blocks → 7 fold layers → 1 root proof
1000 blocks → 10 fold layers → 1 root proof

All leaf proofs → PRUNED
All transactions → PRUNED
NeXuS stores: current state + root proof chain only
Storage shrinks over time through aggregation.

    All proofs share a canonical circuit shape (common padding target) — the multiverifier is homogeneous, auditable, predictable. Internal folds: M31 channel (fast). Root: Blake2s (anchored, externally verifiable).

    The Note / Nullifier / Channel Model¶

    This replaces account-based balances with a privacy-preserving UTXO-like model:

    Channel → Subchannel → Note (encrypted, ECDH + Poseidon)
                       ↓ spent
                    Nullifier (proves note is spent without revealing WHICH note)

    Why notes instead of balances? - Account balances are linkable — same address receives and sends, observable - Notes are unlinkable — each note is a fresh encrypted value, nullifier breaks the link - Spent notes → nullifiers → compact, prunable set - Only the owner with the viewing key can discover their own notes

    The Viewing Key (scan_key)¶

    Maps directly to the stealth address design from earlier in this session: - viewing_key = scan_key — finds incoming notes without spending key - Owner runs discovery service scan: for each encrypted note, try to decrypt with viewing_key - Successful decryption = this note belongs to me - View tags (1-byte hint per note) let scanner skip 99% of notes without full decryption

    Phase-ordered action model¶

    0 SetViewingKey → 1 OpenChannel → 2 OpenSubchannel → 3 Deposit
→ 4 UseNote → 5 CreateEncNote → 6 Withdraw → 7 InvokeExternal

    InvokeExternal = the anonymizer: call any external NeXuS service (royalty contract, staking, marketplace) from inside a private transaction without revealing the caller. Recipe book royalties flow through InvokeExternal. Creator identity: never exposed.

    Cryptographic primitives¶

    • Poseidon with domain-separation tags — all hashes
    • ECDH with ephemeral keys — note encryption (channel keys, addresses, amounts, tokens, private keys all encrypted)
    • Nullifier = hash(viewing_key, note_id) — spend proof without linkage

    Lean Formal Verification¶

    lean/ directory uses Mathlib4 — the most comprehensive mathematical proof library. Security properties are mathematically proven, not just tested. This is the gold standard for critical cryptographic code. Long-term NeXuS goal: Lean proofs for all core ZK primitives.

    What a Dynamic Bonding Curve Is¶

    A price-discovery launch mechanism where the token price follows a mathematical curve as supply is bought. Early supporters buy in cheap. Price rises with demand. The market sets the value.

    bonding_curve = piecewise constant product across up to 20 price ranges

Each range: x * y = l²  (liquidity l, price range [pa, pb])
Overall:    bonding_curve = function([l_i, pa_i, pb_i] for i in ranges)

Creator configures: starting price, curve shape, fee structure
Market determines: actual price at any moment
